## 技术方案（三层，无任何视觉库）

环境限制：只有 `numpy` + `PIL`，**没有 `cv2` / `scipy` / `skimage`**，
所以 `findContours`、`minAreaRect`、`connectedComponents`、`Otsu` 全部手写。

### 第 1 层：自适应阈值（`vision.py`）

手写 **Otsu 算法**（最大化类间方差），取代硬编码的 `bright > 200`。
实测自动取到 **129** —— 自动适应深色/浅色主题。

同时加**低饱和度**约束：面板是中性灰白，而页面装饰是饱和紫色，
这一步过滤掉大量干扰。

### 第 2 层：找「面板」而不是找「方框」（关键）

**这是整个方案的核心。**

之前失败的做法：全图搜「空心方框」→ **748 个候选**，无法区分。

有效做法：先找**最大的低饱和亮连通域**。实测信噪比：

```
32183   <- 控件面板
 1212
  600
  593
```

**32183 vs 1212 = 27 倍分离度**。这让面板选择**毫无歧义**，不需要调参。

连通域用**手写两遍扫描 + 并查集**（按行游程合并），
1920×1080 全图仅 **0.01 秒**，比逐像素 BFS 快得多。

### 第 3 层：面板内部找复选框

在面板 bbox 内搜索组件，按**方正度**（`min(aspect, 1/aspect)`）排序。

实测面板内**恰好只有 1 个候选**：

```
candidate {'x': 517, 'y': 481, 'w': 39, 'h': 36, 'squareness': 0.923}
```

### 为什么这样能免疫旋转

控件绕 3D 旋转约 **7°**（自动测得 7.59°，与人工测量一致）。
此前用「轴对齐包围盒 + 内缩」会**固定偏 16px**。

现在**把复选框当独立组件找**，它的**自身 bbox 中心**与面板是否旋转**无关**。
这从根上绕开了旋转问题，而不是去补偿它。

## 修掉的 3 个 bug

1. **验证逻辑错了** —— 我最初判断「控件消失 = 成功」，
   但**解开的控件仍留在 DOM 里**，只是变成绿色对勾。
   所以第一次跑完显示 `FAILED`，而截图里明明是 `成功!`。
   改成**像素检测绿色勾**（`green > 120 且高于 R/B 40 以上`）。

2. **等待逻辑错了** —— 我原本等「画面不再变化」，
   但**空白过渡页也完全静止**，于是脚本在页面还没渲染时就放弃了。
   改成**先等控件出现**（反复调用定位器），再等稳定。

3. **旋转填充色引入假边缘** —— 试过「先旋正再检测」，
   候选反而从 748 **涨到 1010**。证明旋转不是主要矛盾，
   填充色处理不当会帮倒忙。最终方案不需要旋正。

## 诚实的限制

### 控件其实**永不静止**

实测漂移轨迹（每 1 秒）：

```
t=0s (506,503) → t=4s (486,476) → t=7s (504,474) → t=12s (488,476) → t=19s (516,481)
```

它在 **478~517 之间持续振荡**，是 3D 晃动的固有特性，**等不到"静止"**。

所以「等稳定」那一步**实际是无效的**。真正让它成功的是：
定位精度（2px）远小于晃动幅度（~40px），**所以随时点都能中**。

这点必须说清楚，免得以为"等稳定"是必需步骤。

### 适用边界

**适合**：
- 单一面板 + 单一复选框的 Turnstile 类控件
- 深色/浅色主题（Otsu 自适应）
- 静止或小幅晃动的控件

**可能失效**：
- 页面上有**多个**同样大的亮面板 → 27× 分离度不再成立
- 控件**快速**移动（单帧内位移 > 控件尺寸）
- 面板与背景**对比度极低**（Otsu 无法分离）
- 复选框被遮挡
