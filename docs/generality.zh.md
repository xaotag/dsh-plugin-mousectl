# 通用性评估：**结论是"不够通用"，而且我之前的说法夸大了**

你问得对。实测数据推翻了我在 `VISION-SOLUTION.md` 里的两个核心说法。

## 实测：去掉"搜索区域"限制后立刻失效

之前所有"漂亮"的数字，都依赖我**手动把搜索范围裁到浏览器内容区**。
一旦去掉这个前提（也就是通用场景），结果完全不同：

| 场景 | 最大组件 | 面板是否最大 | 面板内候选数 | 点在哪 |
|---|---|---|---|---|
| 裁剪到浏览器区（我之前用的） | 32183 | ✅ 是 | **1** | (514,481) 正确 |
| **不裁剪（通用）** | **797231** | ❌ **否** | **17** | (994,366) **错误** |

`797231` 是**整个桌面/页面**。也就是说：

> **我之前说的"27 倍分离度"是裁剪带来的假象**，不是方法本身的鲁棒性。

## 被推翻的两个说法

### 说法一：「面板信噪比 27×，选择毫无歧义」

**不成立。** 不裁剪时，面板（32183）根本不是最大的，
最大的是整页背景（797231）。通用情况下**没有 27× 分离度**。

### 说法二：「面板内恰好只有 1 个候选」

**不成立。** 不裁剪时是 **17 个候选**。我看到的"恰好 1 个"，
是因为裁剪后**把面板外的干扰项切掉了**。

## 更严重的：在正放的 2captcha 页面上几乎失效

那个页面（我之前用来验证"Turnstile 能否通过"的）：

```
ts-upright-before.png:
   top areas = [586912, 405478, 93463, 51834]
   dominance = 1.4x          <- 面板根本不突出
```

**1.4 倍**，不是 27 倍。页面主体（586912）比面板还大。
这个页面上"找最大亮块"的策略**基本靠运气**。

讽刺的是：恰恰是这个页面**不需要**视觉定位（控件正放、DOM 可读），
而真正需要视觉定位的 nowsecure，我又是靠手工裁剪才让它工作的。

## 根本问题

现在的实现**不是"通用的视觉定位器"**，而是：

> **一个针对特定截图、在手工指定裁剪区域内、针对单个 Turnstile 控件的特化脚本。**

它隐含依赖了这些**没有自动满足**的前提：

| 隐含假设 | 现实 |
|---|---|
| 已知浏览器内容区的屏幕坐标 | 需要 CDP 先测出来，多显示器/缩放会更复杂 |
| 控件是画面中最大的亮块 | 不成立，整页背景往往更大 |
| 面板内只有一个方形组件 | 不成立，17 个 |
| 控件是 Turnstile 样式 | 换个 UI 就失效 |
| 控件在画面中央附近 | 未验证 |

## 要真正通用，需要补什么

按难度排序：

1. **自动确定搜索区域**（低）—— 用窗口矩形 API，而不是手工裁剪。
   这是最小改动，能救回一大半。但没解决根本问题。
2. **面板判据换成形状先验**（中）—— 不能只看"最大"，
   要按**长宽比接近已知控件比例 + 边界完整 + 内部有方形子组件**来打分。
   这需要引入"控件模板"概念，通用性变成"同族控件"级别。
3. **多尺度、多假设搜索**（中高）—— 滑动窗口 + 打分排序，
   而不是"选最大然后寄希望于它是对的"。
4. **真正的通用点击器**（高）—— 需要模板库或学习模型。
   你明确排除了 YOLO，那么只能做到"模板匹配"级别。

## 诚实的重新评价

| 我之前说的 | 实际情况 |
|---|---|
| "纯视觉定位成功，精度 2px" | ✅ 事实，但**在手工裁剪后** |
| "27× 分离度，毫无歧义" | ❌ 裁剪造成的假象 |
| "面板内恰好 1 个候选" | ❌ 裁剪造成的假象 |
| "3/3 通过" | ✅ 事实，但**不能外推到其他页面** |

**它可以作为一个"已知控件的专用定位器"使用**，
但**不能称为通用视觉点击器**，我也不该用"毫无歧义"这种词。

## 建议

如果要继续，**第 1 步（自动确定搜索区域）性价比最高** ——
把手工裁剪换成窗口矩形，能立刻让它"开箱可用"，
但要说清：它仍然是**Turnstile 专用**的，不是通用的。

要真正的通用性，得接受"模板库"路线，那是另一个量级的工程。
在你排除 YOLO/OpenCV 的前提下，我认为**不划算**。
